## User Scenarios & Testing *(mandatory)*

### User Story 1 - 결혼 준비 공간과 할 일 관리 (Priority: P1)

예비부부는 자신의 웨딩 공간을 만들고 결혼 예정일, 준비 할 일, 담당자와 마감일을
관리한다. 요약 화면에서 진행률과 다음에 해야 할 일을 확인한다.

**Why this priority**: 준비 업무의 누락을 줄이며 다른 관리 기능 없이도 핵심 가치를 제공한다.

**Independent Test**: 새 사용자가 웨딩 생성, 할 일 등록·수정·완료, 요약 확인을 수행한다.

**Acceptance Scenarios**:

1. **Given** 로그인한 새 사용자, **When** 웨딩 이름과 예정일을 입력해 생성,
   **Then** 사용자가 소유자가 되고 기본 준비 목록과 남은 일수를 확인한다.
2. **Given** 예정일 미정, **When** 날짜 없이 생성, **Then** 공간이 생성되고
   남은 일수와 날짜에 의존하는 마감일은 미정으로 표시된다.
3. **Given** 준비 목록, **When** 할 일 추가·수정·완료·완료 취소·삭제,
   **Then** 확인된 변경이 다시 방문해도 유지되고 진행률은 완료 수/전체 수와 일치한다.
4. **Given** 예정일 기준 마감과 직접 정한 마감이 공존, **When** 결혼 예정일 변경,
   **Then** 기준일 연동 마감만 변경되고 변경 내역이 표시된다.
5. **Given** 준비 데이터, **When** 요약 확인, **Then** 미완료 마감 경과 항목,
   오늘부터 7일 이내 마감 항목, 날짜 미정 항목이 구분된다.

### User Story 2 - 예산과 지출 관리 (Priority: P1)

예비부부는 총예산을 정하고 항목별 예상 비용, 확정 비용과 지급 내역을 기록해
초과 예산과 남은 지급액을 파악한다.

**Why this priority**: 결혼 준비에서 비용의 누락과 중복 합산을 방지한다.

**Independent Test**: 빈 웨딩에 비용 항목과 지급 기록만 등록해 합계와 잔액을 검증한다.

**Acceptance Scenarios**:

1. **Given** 총예산 10,000,000원, 항목 A 예상 3,000,000원·확정 3,200,000원,
   항목 B 예상 2,000,000원·확정 미정, **When** 예산 확인,
   **Then** 예상 합계 5,000,000원, 확정 합계 3,200,000원,
   전망 합계 5,200,000원, 예산 대비 잔액 4,800,000원을 표시한다.
2. **Given** A의 확정 비용 3,200,000원, **When** 1,000,000원과 500,000원 지급 기록,
   **Then** 지급 합계 1,500,000원과 미지급액 1,700,000원을 표시한다.
3. **Given** 비용 미입력 또는 총예산 미정, **When** 합계 확인,
   **Then** 누락 항목 수를 표시하고 총예산 미정 시 잔액은 미정으로 표시한다.
4. **Given** 예산 초과 또는 지급액이 확정 비용보다 큼, **When** 저장,
   **Then** 초과액을 표시하며 명시적으로 확인하면 실제 금액을 기록할 수 있다.
5. **Given** 음수·소수 원 단위 금액, **When** 저장,
   **Then** 항목별 오류를 설명하고 해당 입력을 저장하지 않는다.

### User Story 3 - 파트너와 공동 준비 (Priority: P2)

웨딩 소유자는 파트너를 편집자로 초대하고 함께 준비 정보를 수정한다.

**Why this priority**: 역할과 책임을 나누되 개인 웨딩 정보의 접근 범위를 통제한다.

**Independent Test**: 소유자·초대된 편집자·비구성원 계정으로 접근과 편집을 비교한다.

**Acceptance Scenarios**:

1. **Given** 소유자, **When** 특정 계정을 초대하고 대상이 7일 안에 수락,
   **Then** 대상만 편집자로 합류하며 소유자는 구성원 목록을 확인한다.
2. **Given** 만료·철회·이미 사용된 초대 또는 다른 계정, **When** 수락 시도,
   **Then** 합류가 거부되고 소유자는 새 초대를 만들 수 있다.
3. **Given** 편집자, **When** 준비 데이터를 수정하거나 구성원 관리·웨딩 삭제 시도,
   **Then** 데이터 수정은 허용하고 구성원 관리·웨딩 삭제는 거부한다.
4. **Given** 제거된 구성원 또는 비구성원, **When** 조회·수정·내보내기 시도,
   **Then** 모든 접근을 거부한다. 제거 전 열어 둔 화면의 이후 작업도 거부한다.
5. **Given** 같은 항목을 두 사람이 편집, **When** 먼저 저장된 변경 이후 오래된 값 저장,
   **Then** 조용히 덮어쓰지 않고 충돌과 최신 값을 제시해 재편집하게 한다.

---

### User Story 4 - 업체 후보 비교와 선택 기록 (Priority: P2)

사용자는 예식장, 촬영, 의상 등 업체 후보를 직접 등록해 견적과 상담 진행을 비교한다.

**Why this priority**: 거래 기능 없이도 여러 후보의 결정 근거를 한곳에 정리할 수 있다.

**Independent Test**: 업체 후보 3개를 등록하고 비교·상태 변경·비용 연결을 확인한다.

**Acceptance Scenarios**:

1. **Given** 업체 후보 없음, **When** 이름·분류·선택적 견적·연락처·메모를 입력,
   **Then** 후보를 저장하고 같은 분류 후보의 견적과 상태를 함께 비교한다.
2. **Given** 후보, **When** 관심·상담 예정·상담 완료·선택·제외로 상태 변경,
   **Then** 상태와 수정자가 기록되고 제외 후보도 다시 조회할 수 있다.
3. **Given** 선택 업체, **When** 기존 비용 항목에 연결하거나 새 항목 생성 후 연결,
   **Then** 비용 합계에는 연결된 비용 항목만 한 번 반영하고 견적은 중복 합산하지 않는다.
4. **Given** 연결된 업체, **When** 업체 삭제, **Then** 확인 후 업체와 연결만 제거하며
   기존 비용 항목과 지급 기록은 보존한다.

### User Story 5 - 하객과 참석 여부 관리 (Priority: P3)

사용자는 하객 목록과 초대·참석 상태를 관리해 예상 인원을 파악한다.

**Why this priority**: 준비 핵심 흐름이 확보된 후 식사 및 초대 규모를 정리한다.

**Independent Test**: 업체나 예산 등록 없이 하객을 등록하고 인원 집계를 검증한다.

**Acceptance Scenarios**:

1. **Given** 하객 없음, **When** 이름·구분·선택적 연락처·동반 인원을 등록,
   **Then** 저장되며 연락처 없이도 하객을 관리할 수 있다.
2. **Given** 동일 이름 또는 연락처 후보, **When** 하객 추가,
   **Then** 중복 가능성을 안내하고 사용자가 확인하면 별도 사람으로 저장한다.
3. **Given** 참석 하객 2명 중 한 명 동반 인원 2명, 불참 1명, 미정 1명,
   **When** 집계, **Then** 확정 참석 4명, 불참 등록 1명, 미정 등록 1명을 구분한다.
4. **Given** 하객 목록, **When** 초대 상태 또는 참석·불참·미정 변경과 검색·필터,
   **Then** 선택 조건에 맞는 목록과 집계를 확인한다.

---

### User Story 6 - 데이터 보관과 서비스 종료 (Priority: P2)

사용자는 준비 기록을 내보내고 소유자는 더 이상 필요한 웨딩 공간을 삭제한다.

**Why this priority**: 개인 정보에 대한 통제와 서비스 종료 시 데이터 이동을 보장한다.

**Independent Test**: 샘플 웨딩을 내보내 원본과 비교하고 삭제 후 접근 차단을 확인한다.

**Acceptance Scenarios**:

1. **Given** 인증된 구성원, **When** 데이터 내보내기,
   **Then** 기본 정보·할 일·예산·지급·업체·하객이 포함된 다운로드 가능한 자료를 받는다.
2. **Given** 소유자, **When** 삭제 대상과 복구 불가 안내를 읽고 명시적 확인,
   **Then** 모든 구성원 접근과 초대가 즉시 차단되고 웨딩 데이터가 삭제된다.
3. **Given** 저장 실패 또는 반복 제출, **When** 저장·재시도,
   **Then** 실패를 완료로 표시하지 않고 입력을 보존하며 같은 제출이 중복 생성되지 않는다.
4. **Given** 모바일 화면이나 키보드 사용, **When** 주요 등록·편집·내보내기 수행,
   **Then** 레이블과 오류 안내를 확인하고 모든 필수 조작을 완료할 수 있다.

---

### Edge Cases

- 할 일이 0개면 진행률은 0%와 준비 항목 없음으로 표시한다. 완료 항목은 마감 경과에서 제외한다.
- 예정일이 과거여도 기록 관리는 허용하고 남은 일수 대신 경과 일수를 표시한다.
- 날짜를 미정으로 바꾸면 기준일 연동 마감은 미정으로 전환하고 직접 정한 날짜는 유지한다.
- 기준일 연동 마감이 과거가 되면 완료 처리하지 않고 마감 경과로 표시한다.
- 총예산 0원과 미정은 구분한다. 비용 0원도 유효하며 빈 금액과 구분한다.
- 확정 비용 미정 항목의 지급 기록은 허용하되 해당 미지급액은 미정으로 표시한다.
- 업체 분류별 선택 후보는 여러 개를 허용하며 선택이 실제 계약이나 결제를 의미하지 않는다.
- 담당 구성원 제거 시 할 일은 유지하고 담당자를 미배정으로 바꾼다.
- 삭제된 항목을 열어 둔 구성원의 수정은 거부하고 목록 갱신을 안내한다.
- 연결이 끊기면 저장 미완료와 재시도 방법을 표시한다. 오프라인 자동 동기화는 범위 밖이다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 서비스는 계정 생성, 로그인, 로그아웃, 계정 접근 복구를 제공해야 한다(MUST).
  수용 기준: 사용자는 새 계정과 복구된 계정으로 자신의 웨딩을 열 수 있고 로그아웃 후 접근은 거부된다.
- **FR-002**: 사용자는 웨딩 이름과 선택적 예정일로 공간을 만들고 수정할 수 있어야 한다(MUST).
  수용 기준: 생성자는 소유자가 되며 예정일 없음·과거 날짜도 Story 1과 경계 조건대로 처리한다.
- **FR-003**: 서비스는 예식장·촬영·의상·초대 준비의 기본 할 일을 제공하고
  사용자별 추가·수정·삭제·완료·완료 취소를 지원해야 한다(MUST). 수용 기준: Story 1.3.
- **FR-004**: 할 일은 제목, 분류, 구성원 담당자 또는 미배정, 상태, 선택적 마감·메모를
  가져야 한다(MUST). 직접 날짜와 예정일 대비 일수 방식의 마감을 구분한다. 수용 기준: Story 1.4.
- **FR-005**: 요약은 예정일·남은 일수·진행률·마감 경과·7일 이내 마감·예산 현황을
  표시해야 한다(MUST). 비용 없는 공간은 입력 안내를 표시한다. 수용 기준: Story 1.2–1.5, Story 2.1–2.3.
- **FR-006**: 서비스는 총예산과 분류별 비용 항목의 이름·예상·확정 금액을 관리해야 한다(MUST).
  금액은 미정 또는 0 이상의 정수 원 단위다. 수용 기준: Story 2.1, 2.3, 2.5.
- **FR-007**: 예상·확정·지급 합계를 각각 표시하고, 전망 합계는 각 항목의 확정 비용이
  있으면 확정 비용, 없으면 예상 비용을 한 번만 더해야 한다(MUST).
  예산 잔액은 총예산에서 전망 합계를 뺀 값이다. 수용 기준: Story 2.1.
- **FR-008**: 지급 기록은 비용 항목·금액·지급일·선택적 메모를 가지며 추가·수정·삭제를
  지원해야 한다(MUST). 항목별 미지급액은 확정 비용에서 지급 합계를 뺀 값이다.
  수용 기준: Story 2.2, 확정 미정 시 경계 조건 적용.
- **FR-009**: 예산 및 지급 초과는 금액을 표시하고 확인 후 저장하며, 미입력 금액은 합산에서
  제외하되 누락 개수를 표시해야 한다(MUST). 수용 기준: Story 2.3–2.5.
- **FR-010**: 소유자는 대상 계정 지정 초대·철회·재초대·구성원 제거를 할 수 있어야 한다(MUST).
  초대는 7일간 유효하고 1회만 수락되며 편집자는 다른 구성원을 관리할 수 없다.
  수용 기준: Story 3.1–3.3.
- **FR-011**: 소유자·편집자는 준비 데이터 조회·편집·내보내기가 가능하며 웨딩 삭제는
  소유자만 가능해야 한다(MUST). 비구성원·제거된 구성원의 이후 작업은 모두 거부한다.
  수용 기준: Story 3.3–3.4, Story 6.2.
- **FR-012**: 서비스는 동시 수정 충돌을 설명하고 최신 값 확인 후 재편집하도록 해야 하며,
  변경된 항목의 최근 수정자와 수정 시각을 제공해야 한다(MUST). 수용 기준: Story 3.5, Story 4.2.
- **FR-013**: 업체 후보 등록·편집·삭제·분류별 비교·상태 관리를 제공해야 한다(MUST).
  이름과 분류는 필수이며 견적·연락처·상담일·메모는 선택이다. 수용 기준: Story 4.1–4.2.
- **FR-014**: 업체 후보와 비용 항목 연결은 후보별 최대 1개이며 사용자의 명시적 조작으로
  수행해야 한다(MUST). 업체 견적이나 선택 상태 변경은 비용을 자동 변경하지 않는다.
  수용 기준: Story 4.3–4.4; 견적 수정 후 기존 비용 및 합계 유지 확인.
- **FR-015**: 하객 이름·구분(신랑 측/신부 측/공동/기타)·선택적 연락처·동반 인원·
  초대 상태(미초대/초대 완료)·참석 상태(미정/참석/불참)를 관리해야 한다(MUST).
  동반 인원은 0 이상의 정수다. 수용 기준: Story 5.1, 5.4 및 음수·소수 동반 인원 저장 거부.
- **FR-016**: 하객 이름 검색·구분 및 상태 필터·중복 안내·참석 집계를 제공해야 한다(MUST).
  확정 참석은 참석 상태 하객의 본인과 동반 인원 합계이며 미정·불참은 포함하지 않는다.
  수용 기준: Story 5.2–5.4.
- **FR-017**: 구성원은 웨딩의 기록을 내보낼 수 있어야 한다(MUST). 자료는 내보내는 시점의
  저장된 값과 일치하고 다른 웨딩이나 인증 정보를 포함하지 않는다. 수용 기준: Story 6.1, Story 3.4.
- **FR-018**: 삭제는 대상·영향 확인 후 실행해야 한다(MUST). 비용 항목 삭제 시 연결된 지급
  기록 삭제도 안내하며, 웨딩 삭제 시 전체 기록과 초대를 삭제한다. 수용 기준: Story 6.2;
  비용 항목 삭제 취소 시 원본 유지, 확인 시 지급 기록과 합계도 반영.
- **FR-019**: 저장 실패 시 입력을 유지하고 재시도를 제공하며 중복 제출·오래된 수정으로
  데이터가 중복되거나 조용히 덮어써지지 않아야 한다(MUST). 수용 기준: Story 3.5, Story 6.3.
- **FR-020**: 로그인한 구성원만 개인정보에 접근하며 연락처는 선택 수집해야 한다(MUST).
  개인정보를 담은 오류·운영 기록을 남겨서는 안 된다. 수용 기준: Story 3.4, Story 5.1;
  오류 기록 검토에서 하객 연락처·인증 정보 원문 0건.
- **FR-021**: 웨딩 삭제 후 활성 자료는 즉시 제거하고 복구용 보관 사본은 최대 30일 내
  제거해야 한다(MUST). 그 기간 중 복구가 발생해도 삭제 웨딩의 접근을 재개하지 않는다.
  수용 기준: Story 6.2와 삭제 수명 검토. 결혼 예정일 경과만으로는 자동 삭제하지 않는다.
- **FR-022**: 핵심 여정은 모바일·데스크톱 및 키보드로 완료 가능하고 레이블·필드 오류·
  텍스트 상태·로딩·빈 목록·실패·완료 안내를 제공해야 한다(MUST). 수용 기준: Story 6.4.

### Key Entities *(include if feature involves data)*

- **사용자**: 계정, 표시 이름, 본인 접근 복구 정보. 여러 웨딩에 참여할 수 있다.
- **웨딩 공간**: 이름, 선택적 예정일, 소유자, 총예산, 생성·수정 시각. 준비 기록의 소속 단위다.
- **구성원 및 초대**: 사용자와 웨딩의 역할, 초대 대상, 유효기간, 수락·철회 상태.
- **할 일**: 웨딩 소속, 제목, 분류, 담당자, 상태, 마감 방식·값, 메모, 최근 수정자·시각.
- **비용 항목**: 웨딩 소속, 이름, 분류, 예상 비용, 확정 비용, 선택적 업체 연결.
- **지급 기록**: 비용 항목 소속, 금액, 지급일, 메모. 실제 결제 실행이 아닌 사용자 기록이다.
- **업체 후보**: 웨딩 소속, 이름, 분류, 선택적 견적·연락처·상담일·메모, 상태.
- **하객**: 웨딩 소속, 이름, 구분, 선택적 연락처, 동반 인원, 초대·참석 상태.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 첫 사용 예비부부 10명 중 9명 이상이 도움 없이 5분 이내 웨딩 생성과
  첫 할 일 등록을 완료한다. 예정일 미정 사용자도 포함한다.
- **SC-002**: 같은 평가에서 9명 이상이 1분 이내 다음 마감 업무와 진행률을 찾는다.
- **SC-003**: 금액 0원·미정·초과·여러 지급·수정·삭제를 포함한 인수 자료에서
  합계·잔액·미지급액의 원 단위 불일치가 0건이다.
- **SC-004**: 구성원·비구성원·제거 계정·다른 초대 대상·만료 초대의 권한 검증에서
  허용되지 않은 조회·변경·내보내기·삭제가 0건이다.
- **SC-005**: 100명이 동시에 사용하고 웨딩당 할 일 200개·비용 100개·업체 100개·
  하객 1,000명이 있을 때 안정적인 연결에서 요약·목록 표시와 저장 결과 확인의
  95%가 각 2초 이내 완료된다.
- **SC-006**: 모바일 및 데스크톱 사용성 평가의 10명 중 9명 이상이 할 일 완료,
  비용 등록, 하객 참석 변경을 도움 없이 수행하고 8명 이상이 준비 현황 파악을
  5점 만점 중 4점 이상으로 평가한다.
- **SC-007**: 동시 수정·반복 제출·저장 실패 인수 시나리오에서 안내 없는 데이터 손실과
  중복 생성이 0건이며, 내보낸 모든 값은 저장된 원본과 일치한다.
- **SC-008**: 삭제 인수 시나리오의 100%에서 즉시 접근이 차단되고 최대 30일 보관 정책의
  제거 확인 기록이 존재한다. 키보드만으로 모든 필수 조작을 완료할 수 있다.

## Assumptions

- 요청에 상세 범위가 없어 예비부부의 공동 준비 도구를 초기 서비스로 가정했다.
  전문 플래너용 고객 관리, 업체 판매자 계정, 공개 업체 검색·후기·추천, 거래 중개,
  예약 확정, 전자 계약, 실제 결제, 축의금 관리, 좌석 배치는 제외한다.
- 초기 언어는 한국어, 통화는 KRW(정수 원), 날짜·시간 기준은 Asia/Seoul이다.
  네이티브 앱, 다른 통화·언어, 외부 달력 연동, 이메일·문자·푸시 알림은 제외한다.
  마감 안내는 서비스 안에서 확인하는 요약으로 제공한다.
- 소유자는 1명, 편집자는 여러 명이다. 소유권 이전·열람 전용 역할·계정 자체 삭제는
  이번 범위에서 제외하며 웨딩 데이터 삭제는 포함한다.
- 업체·하객·지급 정보는 구성원이 직접 입력하며 외부 서비스에서 자동 수집하지 않는다.
  하객의 직접 참석 응답 화면과 파일 가져오기는 제외한다.
- 저장에는 연결이 필요하다. 데이터 입력은 필수 항목만 요구하며 이름·할 일 제목은
  1–100자, 메모는 최대 2,000자, 금액은 0–999,999,999,999원,
  동반 인원은 0–99명을 허용한다. 초과 입력은 저장 전에 항목별로 설명한다.
- 주요 의존성은 사용자 계정 확인·접근 복구, 내보내기 제공, 삭제와 보관 사본 제거를
  검증할 운영 절차다. 현재 프로젝트에 이를 제공하는 기존 서비스는 확인되지 않았다.
- 성공 기준의 시간·인원은 초기 출시 검증 목표다. 사용성 평가는 실제 대상 사용자로
  수행하며 품질 체크리스트 통과가 구현 또는 출시 목표 달성을 의미하지 않는다.
