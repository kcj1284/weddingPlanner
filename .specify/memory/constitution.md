# Wedding Planner Constitution

## Core Principles

### I. 사용자 여정과 명세 우선

모든 기능은 예비부부의 준비 업무를 줄이는 사용자 시나리오, 우선순위, 검증 가능한
인수 조건을 명세에 정의한 뒤 구현해야 한다(MUST). 명세는 사용자에게 필요한 결과를
기술하고 기술 선택은 구현 계획에 기록해야 한다(MUST). 범위 변경은 명세와 관련 작업에
반영해야 한다(MUST). 이 원칙은 필요가 확인되지 않은 기능의 확장을 방지한다.

### II. 개인정보 최소 수집과 권한 분리

개인정보는 명세에 정의한 목적에 필요한 항목만 수집해야 한다(MUST). 모든 웨딩의 데이터는
인증된 구성원에게만 허용하고, 읽기·수정·초대·삭제 권한을 작업마다 검사해야 한다(MUST).
초대 철회와 구성원 제거는 이후 접근을 차단해야 한다(MUST). 운영 기록에 비밀번호,
인증 정보, 하객 연락처 등 민감한 원문을 남기면 안 된다(MUST NOT).
데이터 내보내기·삭제·보존 범위는 기능 명세와 운영 정책에 명시해야 한다(MUST).

### III. 예산과 일정의 정확성 및 변경 안전성

금액은 명시한 통화와 최소 단위를 기준으로 정확하게 계산해야 한다(MUST).
예상 비용·확정 비용·지급 기록을 구분하고 미입력 값을 0원으로 오인하게 표시하면
안 된다(MUST NOT). 날짜, 시간대, 일정 변경의 영향을 일관되게 처리해야 한다(MUST).
저장 실패·중복 제출·동시 편집으로 확정된 데이터를 조용히 잃거나 중복 생성하면
안 된다(MUST NOT). 파괴적 변경에는 대상과 영향을 표시하고 명시적 확인을 받아야 한다(MUST).

### IV. 핵심 위험에 맞춘 검증

예산 합계, 날짜 변경, 웨딩 간 접근 차단, 초대 권한, 동시 수정, 데이터 삭제의
규칙을 변경할 때는 관련 자동 검증을 추가하거나 갱신해야 한다(MUST).
핵심 사용자 여정에는 정상·권한 거부·입력 오류·저장 실패의 인수 검증을 수행해야 한다(MUST).
발견된 결함에는 해당 결함의 재발을 검출하는 검증을 남겨야 한다(MUST).
문서나 단순 표시 수정은 영향에 맞는 검토로 검증하고 구현을 그대로 복제하는 테스트는
만들지 않는다. 검증 결과는 검토자가 확인할 수 있게 기록해야 한다(MUST).

### V. 사용성, 접근성 및 단순성

핵심 업무는 모바일과 데스크톱에서 완료할 수 있어야 한다(MUST). 입력에는 의미 있는
레이블, 오류 설명, 키보드 접근, 색상 이외의 상태 표시를 제공해야 한다(MUST).
로딩·빈 목록·실패·저장 완료를 구분해서 사용자가 다음 행동을 판단할 수 있어야 한다(MUST).
의존성이나 구조를 추가할 때는 현재 명세의 필요와 유지 비용을 계획에 기록해야 한다(MUST).
운영 오류는 개인정보를 노출하지 않는 기록으로 원인을 추적할 수 있어야 한다(MUST).

## 서비스 제약 및 데이터 기준

- 초기 대상은 한국어로 결혼을 준비하는 예비부부다. 통화와 시간대 기본값은 기능 명세에
  명시하며 다른 시장 지원은 별도 범위로 검토한다.
- 업체 후보 관리, 계약 상태 기록, 지급 기록과 실제 중개·계약 체결·결제 실행을 구분한다.
  외부 거래 실행은 별도 명세와 검증 없이는 추가하지 않는다(MUST NOT).
- 기능 명세는 포함 범위, 제외 범위, 역할, 데이터 수명, 측정 가능한 성공 기준을
  명시해야 한다(MUST). 기술 스택은 이 헌장에서 고정하지 않는다.
- 데이터 저장 방식 변경에는 기존 데이터의 유지·이관·복구 방법을 기록해야 한다(MUST).
  운영 데이터에 영향을 주는 변경은 적용 전에 복구 가능성을 검증해야 한다(MUST).

## 개발 절차 및 품질 관문

1. 명세 작성과 요구사항 품질 검토를 완료한다. 가정과 미결정 사항을 기록한다.
2. 구현 계획에서 헌장 준수, 기술 선택, 개인정보·예산·일정 관련 위험을 검토한다.
3. 우선순위와 의존성을 반영한 작업을 만들고 검증 가능한 사용자 여정 단위로 구현한다.
4. 병합 전 변경 내용, 인수 조건, 위험에 맞는 검증 결과, 헌장 준수를 검토한다.
5. 배포 전 핵심 여정 검증과 데이터 변경의 복구 검증 결과를 확인한다.

원칙 예외가 필요한 경우 해당 원칙, 이유, 영향, 대안, 해소 조건을 계획에 기록하고
프로젝트 책임자의 승인 근거를 남겨야 한다(MUST). 기록되지 않은 예외는 허용하지 않는다.

## Governance

이 헌장은 프로젝트의 명세·계획·구현·검토 기준이다. 템플릿의 예시 문구는 프로젝트
규칙을 대신하지 않는다. 각 명세와 구현 계획은 적용 가능한 원칙의 준수 여부를 검토하고,
각 변경 검토는 명세 및 인수 조건과의 일치 여부를 확인해야 한다(MUST).

개정 제안에는 이유, 변경된 규칙, 기존 명세 및 구현에 미치는 영향, 필요한 이관 작업을
기록해야 한다(MUST). 프로젝트 책임자가 개정을 승인하면 헌장의 버전과 최종 개정일을
갱신한다. 기존 문서 및 구현에 필요한 후속 작업은 별도 작업으로 추적한다.

버전은 MAJOR.MINOR.PATCH를 따른다. 원칙의 삭제나 호환되지 않는 재정의는 MAJOR,
원칙 또는 규범의 추가·실질적 확장은 MINOR, 의미를 바꾸지 않는 설명·오탈자 수정은
PATCH를 올린다. 최초 제정은 1.0.0으로 기록한다.
